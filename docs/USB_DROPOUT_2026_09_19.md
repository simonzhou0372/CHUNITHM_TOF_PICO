# Pico USB 掉线复核与修复（2026-09-19）

后续版本见 [2026-09-20 非阻塞排查与修复](USB_DROPOUT_2026_09_20.md)。本文保留当轮记录；当前固件已用异步 I2C 替代有界同步读取，并启用分步 ToF 恢复。

## 结论和证据边界

用户观察：运行中偶发 USB 掉线，LED 常亮，多数能自行重连，少数需要拔插。
本轮检查的是当前工作区（已有多处未提交的历史修复），不是假定板内固件一定
与源码相同。未连接硬件调试器，不能宣称已复现用户现场或确认唯一根因。

确认的代码问题及处理：

| 问题 | 后果 | 本次修改 |
| --- | --- | --- |
| SDK 2.3.0 读取函数等待 TX FIFO 空位时没有检查超时 | 若 FIFO 一直满，Core0 可以停止服务 USB；Core1 也有相同漏洞 | 两条总线均使用项目内有界读取函数 |
| MPR121 把所有非负 I2C 返回值视为成功 | 数据 NACK 时 SDK 可返回短写/0，仍进入后续读取 | 核对返回长度，失败继续原有计数及保留旧触摸状态策略 |
| USB 在 MPR121 初始化的约 800 ms 固定等待之前连接 | 启动及复位重连时不能及时处理枚举请求 | 传感器启动完成后再连接 USB |
| 看门狗只覆盖运行期 | 复位后若再次卡在初始化，无法自动再次复位 | 初始化使用 8 s，看门狗在运行期收紧至原有 2 s |
| printf 禁用且 stdio 后端关闭，原 STATUS 实际无法读出现场 | 重连后无法区分看门狗复位和单纯 USB 问题 | 新增不依赖 printf 的 `USBSTATUS` |
| LED IRQ 读取 Core0 正在修改的 64 位时间戳 | RP2040 上可能读取到不一致时间戳而误报 LED 状态 | 主循环计算状态，IRQ 只读单字节标志 |

I2C 缺陷已与[官方 SDK 2.3.0 源码](https://github.com/raspberrypi/pico-sdk/blob/2.3.0/src/rp2_common/hardware_i2c/i2c.c#L286-L287)
及本机安装文件核对。历史报告“所有 I2C 等待均有超时”的说法已更正。
FIFO 满的故障注入证明原等待条件缺少退出机制，不代表已证明日常轮询必然进入该状态。

为减少时钟裕量干扰，系统时钟由固定 150 MHz 改为 125 MHz。
这是稳定性措施，不是已经证明 150 MHz 导致本次掉线；USB 仍使用其独立时钟。

## 检测逻辑保持

- `slider.cpp`、`air.cpp`、ToF 快照/检测处理没有修改。
- MPR121 寄存器初始化、模式、阈值、轮转顺序、触摸位图及失败保留旧状态策略不变。
- VL53L0X 初始化内容、400 kHz I2C、20000 us 测量预算、距离筛选和恢复策略不变。
- 键盘映射、NKRO 报告格式、按键保持时间不变。
- 每个 I2C 控制器仍由原来的核独占；错误返回不会复位传感器或另一条总线。

`i2c_bounded.h` 只替换底层读取，成功时保持逐字节读取和 RESTART/STOP 行为。
失败时请求禁用本控制器并清除软件 RESTART 标志，不等待总线释放；下次事务
仍按 SDK 的流程重新启用控制器。不会发 XSHUT、重写阈值或自动重试。
物理上一直拉低的总线仍可能需要修复接线/供电，这一修改保证的是软件等待有界。
中断抢占和 Flash 操作不计入 I2C 等待截止时间的保证范围。

USB 挂起/恢复状态同步到 TinyUSB 实际状态，恢复后强制重发当前按键报告。
现有 `CHUNI_USB_AUTO_RECOVERY_ENABLE=0` 保持不变，不新增周期性软断开。

## LED 和复位记录

当前 LED 由 10 ms 定时器驱动，常亮表示观察到某一主循环阶段停留超过 50 ms。
这可以是长操作，也可以是永久等待；IRQ 停止执行时 LED 还可能停留在原电平。
历史固件曾有“最大耗时超过 5 ms 后永久常亮”的逻辑，更不能用旧 LED 单独定因。

运行期看门狗只能在完整主循环结束时喂狗。若未暂停于调试器、时钟/供电正常，
阻塞超过约 2 s 会复位，因此用户所述“多数自行重连”与此机制相符。
复位后 `prev` 是被中断前的主循环阶段；若实际卡在 IRQ，它不等同于 IRQ 内 PC。
`prev=TUD_TASK` 也不能直接排除当时有 USB IRQ 阻塞，需要 SWD 栈/PC 才能进一步定位。

## 使用 USBSTATUS

刷入 `build/Chuni245Tof.uf2`，在设备 CDC 串口发送一行：

```text
USBSTATUS
```

打开串口时启用 DTR。默认固件就支持此命令，不需要开启 printf。
回复示例（仅说明格式）：

```text
USB boot=2 wdt=1 prev=SLIDER loops=123456 core1=654321 gap_us=900 mpr=0,0,0 mount=1 suspend=0 sys_khz=125000
```

- `wdt=1`：硬件记录上一次复位由看门狗引起。
- `prev` / `loops`：看门狗复位前的阶段/完成循环数。`SENSOR_INIT` 表示启动阶段。
  冷启动或保留数据校验失败时不解读旧 RAM，显示 `IDLE` / 0。
- `core1`：本次启动 Core1 心跳；间隔查询可观察是否递增。
- `gap_us`：本次启动两次 USB task 服务的最大间隔。
- `mpr`：本次启动三颗 MPR121 的通信错误数，重启会重新计数。
- `boot`：只有 SRAM 内容保留且 magic 匹配才延续，不能把它当成掉电/欠压检测器。

每次请求最多排入一条小于 256 字节的回复，TX 空间不足直接跳过，不等待主机。
若没有回复，恢复读取后再查询。不要为了读取诊断重新开启阻塞的 stdio USB 后端。
发生自动重连后应先读取这一行，再断电；拔插会使保留现场不可靠。

## 验证结果与上板检查

已完成：

1. Pico SDK 2.3.0 / GCC 15.2 Release 构建，生成 ELF/UF2。
2. 本机 C++ 故障注入回归：正常字节、RESTART/STOP、FIFO 延迟、TX FIFO 满、
   RX 不返回、中途停住、abort、已过截止时间、跨 32 位时间边界、两总线隔离。
   测试运行生产读取函数；硬件寄存器/时钟为模拟对象，详见 `tests/README.md`。

仍需在用户硬件上验证：

1. 连续游戏/待机运行，覆盖原来掉线所需时间，保留 `USBSTATUS` 结果。
2. 在安全接线条件下模拟传感器无响应，确认对应错误增加、USB/HID 和另一条总线仍工作。
3. 主机睡眠/唤醒、串口打开但不读取、拔插 USB 后能重新枚举及恢复按键。
4. 若仍掉线，记录是否为 `wdt=1`、`prev`、是否有 SAVE 操作，以及 VBUS/3V3 波形。

USB E5/E15 规避在现有 SDK 构建中已启用，不把重复启用当作本轮修复。
TinyUSB `OPT_OS_PICO` 的队列读取忽略等待参数并立即返回，所以不能把
`tud_task()` 的 `UINT32_MAX` 参数单独当作这里的死锁证据。
驱动的 EP0 abort 等待仍依赖 USB 硬件，运行期看门狗用于兜底；无现场证据时不改动 SDK。
SAVE 会暂停双核及 USB 服务，本轮没有改变 Flash 持久化策略。
线缆、供电、ESD 和实际 USB 控制器异常，不能仅通过软件编译/模拟测试排除。
